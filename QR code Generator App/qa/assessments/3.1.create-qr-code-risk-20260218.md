# Risk Profile: Story 3.1 — Create QR Code

Date: 2026-02-18
Reviewer: Quinn (Test Architect)

---

## Executive Summary

- **Total Risks Identified:** 13
- **Critical Risks (score 9):** 2
- **High Risks (score 6):** 4
- **Medium Risks (score 4):** 4
- **Low Risks (score 2–3):** 3
- **Overall Story Risk Score:** 42/100 *(Base 100 − 40 critical − 40 high − 20 medium − 6 low)*

The QR Code creation story carries meaningful risk concentrated in two domains: **security** (UserId injection, input sanitization) and **technical** (third-party library capacity errors and client-side validation bypass). Both critical risks are fully mitigable through standard practices already hinted at in the story; the gate outcome depends on whether those mitigations are confirmed in implementation.

---

## Critical Risks Requiring Immediate Attention

### 1. SEC-001: UserId Sourced from Authenticated Context Not Enforced

**Score: 9 (Critical)**
**Probability:** High (3) — Easy to accidentally bind UserId from the POST body in model binding
**Impact:** High (3) — Attacker could create QR codes attributed to any user, IDOR/privilege escalation

**Affected Components:** `QRCodesController (POST)`, `CreateQRCodeViewModel`, EF Core save

**Mitigation:**
- `UserId` must never appear in `CreateQRCodeViewModel`; always set from `HttpContext.User.GetUserId()`
- Add a server-side unit test asserting the saved record's UserId always matches the authenticated user's ID regardless of form payload
- Code review checklist item: verify no `UserId` field in ViewModel

**Testing Focus:**
- Test: Forge POST with arbitrary `UserId` field → assert saved record's UserId equals authenticated user
- Test: Unauthenticated POST → 401/redirect (covered by `[Authorize]`)

---

### 2. SEC-002: Input Validation Bypass via Direct POST (Circumventing Client-Side Only)

**Score: 9 (Critical)**
**Probability:** High (3) — Client-side regex can always be bypassed with tools like curl/Postman
**Impact:** High (3) — Malformed data (non-ASCII, oversized text) stored in DB; potential downstream rendering issues or stored XSS via notes field

**Affected Components:** `CreateQRCodeViewModel`, `QRCodesController (POST)`, `Create.cshtml`

**Mitigation:**
- Server-side `ModelState.IsValid` check is mandatory before any generate/save
- `[StringLength(100)]` + `[RegularExpression(@"^[a-zA-Z0-9]+$")]` on `DecodedText`
- Notes field: `[StringLength(300)]` + HTML-encode on output to prevent stored XSS
- Anti-forgery token already planned (AC 11)

**Testing Focus:**
- Test: POST >100 chars bypassing client → validation error, nothing saved
- Test: POST non-ASCII chars bypassing client → validation error
- Test: POST XSS payload in Notes → stored value is not executable on render
- Test: POST without CSRF token → rejected (403)

## High Risks

### 3. TECH-001: QR Capacity Overflow (ECC/Version/Text Incompatibility)

**Score: 6 (High)**
**Probability:** Medium (2) — Users actively vary ECC/Version; low version + high ECC + long text is a common failure path
**Impact:** High (3) — Unhandled exception from `Net.Codecrete.QrCodeGenerator` bubbles up as 500 error

**Affected Components:** `QRCodeService.ValidateAndGenerate()`

**Mitigation:**
- Wrap library call in try/catch for `QrCodeGenerator` capacity exceptions
- Return a typed result (e.g., `Result<QrCode, string>`) so controller can surface user-friendly message
- Pre-validate capacity before calling generate (consult library docs for capacity tables or use a capacity-check API)

**Testing Focus:**
- Test: version=1, ECC=H, text="AAAA...A" (>7 chars) → friendly error message, HTTP 200 with form re-displayed
- Test: version=10, ECC=L, 100-char string → success
- Test: edge case version=1, ECC=L, text="A" → success (minimal valid case)

---

### 4. SEC-003: Regex Bypass for ASCII Alphanumeric Constraint

**Score: 6 (High)**
**Probability:** Medium (2) — Unicode homoglyphs, null bytes, or percent-encoded characters could slip through naive regex
**Impact:** High (3) — Unexpected characters passed to QR library may cause exceptions or generate corrupt codes

**Affected Components:** `CreateQRCodeViewModel` (`[RegularExpression]`), `QRCodeService`

**Mitigation:**
- Use anchored regex: `^[a-zA-Z0-9]{1,100}$` (not just character class without anchors)
- Add explicit null/empty check before regex evaluation
- Service layer should also reject non-conforming input as defense in depth

**Testing Focus:**
- Test: Unicode char (e.g., `é`, `中`) → validation error
- Test: whitespace, punctuation → validation error
- Test: null byte injection → validation error
- Test: empty string → validation error (Required)

---

### 5. TECH-002: Third-Party Library Integration Risk

**Score: 6 (High)**
**Probability:** Medium (2) — `Net.Codecrete.QrCodeGenerator` is a well-maintained library but its API surface and exception types are not documented in the story
**Impact:** High (3) — Incorrect API usage could produce silently wrong QR codes or runtime crashes

**Affected Components:** `QRCodeService`

**Mitigation:**
- Wrap library entirely in `QRCodeService`; no direct library calls from controller
- Write integration tests calling the real library with known inputs and verify SVG/matrix output
- Document which library version is pinned in `.csproj`

**Testing Focus:**
- Test: known input text + ECC + version → assert deterministic SVG/bitmap output matches expected
- Test: service returns error object (not exception) on invalid input

---

### 6. DATA-001: QR Code Parameters Persisted Without User Ownership Validation

**Score: 6 (High)**
**Probability:** Medium (2) — If EF Core entity has no FK constraint or if UserId is nullable, orphan records are possible
**Impact:** High (3) — Data integrity violation; records with null UserId could leak across user contexts

**Affected Components:** EF Core entity (`QRCode` model), DB migration

**Mitigation:**
- `UserId` column must be non-nullable with FK to `AspNetUsers`
- EF Core save should be inside a try/catch with `DbUpdateException` handling
- Verify migration enforces NOT NULL on UserId

**Testing Focus:**
- Test: attempt save with null UserId → DB exception caught and surfaced gracefully
- Integration test: verify FK constraint exists on QRCodes table

## Medium Risks

### 7. TECH-003: Redirect After Save Points to Non-Existent Route

**Score: 4 (Medium)**
**Probability:** Medium (2) — AC 10 says "redirect to QR Code Details page or My QR Codes list" but Story 3.3 (Details) may not exist yet
**Impact:** Medium (2) — Users land on 404 after successful save; confusing UX, hides success

**Mitigation:**
- Confirm Story 3.3 route exists before implementing redirect; fall back to My QR Codes list (`/QRCodes/Index`) if not
- Add integration test asserting redirect returns 302 to a valid, reachable URL

---

### 8. PERF-001: Synchronous QR Generation Blocking Request Thread

**Score: 4 (Medium)**
**Probability:** Medium (2) — QR generation is CPU-bound; under concurrent load can starve thread pool
**Impact:** Medium (2) — Degraded response times at scale; not a concern for MVP but is technical debt

**Mitigation:**
- For MVP: acceptable as-is, note as tech debt
- Future: offload to background task or ensure generation is fast enough (<50ms for version ≤10)

---

### 9. OPS-001: Insufficient Logging on Creation Event

**Score: 4 (Medium)**
**Probability:** Medium (2) — AC 12 says "log creation event" but level/structure is unspecified
**Impact:** Medium (2) — Without structured log fields (UserId, QRCodeId, timestamp), incident investigation is impaired

**Mitigation:**
- Log at `Information` level with structured fields: `{UserId}`, `{QRCodeId}`, `{ECC}`, `{Version}`, `{IPAddress}`
- Log at `Warning` level for encoding failures with `{DecodedText.Length}`, `{ECC}`, `{Version}`

---

### 10. BUS-001: No Duplicate Detection — User Creates Identical Codes

**Score: 4 (Medium)**
**Probability:** Medium (2) — No uniqueness constraint mentioned; users can create many identical records
**Impact:** Medium (2) — Bloated database, confusing "My QR Codes" list; not a security issue but degrades UX

**Mitigation:**
- Out-of-scope for this story; document as backlog item
- Consider soft warning ("you already have a code with this text") in a future story

---

## Low Risks

### 11. TECH-004: Client-Side Preview Generates Before Save — State Desync

**Score: 3 (Low)**
**Probability:** Medium (2) — Wireframe shows Generate → Preview then separate Save; user might preview then change inputs without regenerating
**Impact:** Low (1) — Confusing UX but no data corruption (server always regenerates from saved params)

**Mitigation:**
- Disable Save button until a fresh Generate has been performed with the current form values
- Or: generate and save in a single POST (simplest and safest)

---

### 12. OPS-002: Missing Error Handling for DB Connection Failure on Save

**Score: 2 (Low)**
**Probability:** Low (1) — DB availability is high in dev/prod environments
**Impact:** Medium (2) — Unhandled `SqlException` surfaces as unformatted 500 page

**Mitigation:**
- Wrap EF Core `SaveChangesAsync` in try/catch; log and return user-friendly error page

---

### 13. BUS-002: Notes Field Allows Free Text — No Profanity/Content Policy

**Score: 2 (Low)**
**Probability:** Low (1) — Internal tool context implies trusted users
**Impact:** Medium (2) — Minimal; internal application unlikely to have compliance exposure

**Mitigation:**
- Accepted risk for this story; revisit if exposure to external users increases

## Risk-Based Testing Strategy

### Priority 1: Critical Risk Tests
1. **SEC-001** — Forge POST body with arbitrary `UserId`; assert saved record UserId = authenticated user's ID
2. **SEC-001** — Unauthenticated POST → 401 or redirect to login
3. **SEC-002** — Bypass client JS: POST `DecodedText` = 200-char string → `ModelState` invalid, nothing saved
4. **SEC-002** — POST `DecodedText` with Unicode/special chars → validation error
5. **SEC-002** — POST `Notes` containing `<script>alert(1)</script>` → rendered safely (HTML-encoded)
6. **SEC-002** — POST without anti-forgery token → 403

### Priority 2: High Risk Tests
7. **TECH-001** — `QRCodeService.ValidateAndGenerate("AAAA...", ECC=H, version=1)` → returns typed error, no exception thrown
8. **TECH-001** — Controller surfaces user-friendly message when service returns error; form re-displayed with inputs preserved
9. **SEC-003** — `DecodedText` = `"héllo"` → validation error; `"Hello123"` → valid
10. **TECH-002** — Integration test: specific known input → deterministic QR SVG/matrix output
11. **DATA-001** — DB assert: `QRCodes.UserId` NOT NULL FK enforced; FK references `AspNetUsers.Id`

### Priority 3: Medium / Low Risk Tests
12. **TECH-003** — Post success → redirect response is 302 to a reachable URL
13. **OPS-001** — Verify log entry emitted with expected structured fields on creation
14. **TECH-004** — UX flows: Generate then change input → Save uses server-regenerated params (or UI prevents stale save)

## Risk Acceptance Criteria

### Must Fix Before Production
- **SEC-001** — UserId never from form input (Critical)
- **SEC-002** — Full server-side validation enforced (Critical)
- **TECH-001** — Library capacity exceptions caught and surfaced as user errors (High)
- **DATA-001** — NOT NULL FK constraint on UserId confirmed in migration (High)

### Can Deploy with Mitigation
- **SEC-003** — Anchored regex; acceptable with planned server-side validation (High, mitigated by SEC-002)
- **TECH-002** — Service wrapper + integration test for library behavior (High)
- **TECH-003** — Fall back to `/QRCodes/Index` if Details route not available (Medium)
- **PERF-001** — Acceptable at MVP scale; log as known tech debt (Medium)
- **OPS-001** — Add structured fields to log call (Medium, low effort)

### Accepted Risks
- **BUS-001** — No duplicate detection; backlog for future story (PO approval implied)
- **TECH-004** — If single-POST design is chosen, risk is eliminated; accepted otherwise
- **OPS-002** — DB unavailability out of scope for story; generic error handler covers it
- **BUS-002** — Internal tool; content policy risk accepted

## Monitoring Requirements

Post-deployment monitoring:
- **OPS-001**: Structured log query for `QRCodeCreated` events; alert on error spike
- **PERF-001**: P95 response time on `POST /QRCodes/Create`; alert if >500ms
- **SEC-001/002**: Alert on 403 (CSRF) or repeated 400 (validation) spikes from same IP
- **TECH-001**: Log and alert on QR generation failures; track failure rate
