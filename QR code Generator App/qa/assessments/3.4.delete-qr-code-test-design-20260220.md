### AC3: Only the owner can delete their QR code — deleting another user's code returns 404

| ID          | Level       | Priority | Test Description                                                                                                      | Justification                                              | Mitigates Risk |
|-------------|-------------|----------|-----------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------|----------------|
| 3.4-INT-002 | Integration | P0       | POST /QRCodes/Delete/{id} as UserA with UserB's QR code ID → 404 returned; no deletion occurs                        | Core IDOR prevention; ownership verification enforced      | SEC-001        |
| 3.4-INT-003 | Integration | P0       | POST /QRCodes/Delete/{id} as UserA with UserA's QR code ID → 200/302 redirect; QR code deleted from database         | Owner can delete own QR code                               | —              |
| 3.4-INT-004 | Integration | P0       | POST /QRCodes/Delete/{forgedId}?userId={UserB_Id} — forged userId parameter ignored; only authenticated user ID used | Param injection prevention; server sources userId from session only | SEC-001 |
| 3.4-INT-005 | Integration | P0       | Query database after UserA deletes UserB's code (404 returned) → UserB's QR code still exists unchanged              | Verify unauthorized deletion is truly blocked              | SEC-001        |
| 3.4-INT-006 | Integration | P1       | POST /QRCodes/Delete/{nonExistentId} → 404 returned; no exception or 500 error                                       | Non-existent ID handled gracefully                         | —              |

### AC6: Anti-forgery token is required on the delete POST action

| ID          | Level       | Priority | Test Description                                                                                           | Justification                                    | Mitigates Risk |
|-------------|-------------|----------|------------------------------------------------------------------------------------------------------------|--------------------------------------------------|----------------|
| 3.4-INT-013 | Integration | P0       | POST /QRCodes/Delete/{id} without anti-forgery token → 400 Bad Request or validation error returned       | Core CSRF protection enforcement                 | SEC-002        |
| 3.4-INT-014 | Integration | P0       | POST /QRCodes/Delete/{id} with valid anti-forgery token → deletion succeeds (200/302)                      | Valid token allows deletion                      | SEC-002        |
| 3.4-INT-015 | Integration | P1       | POST /QRCodes/Delete/{id} with token from previous page load (replay attack) → validation error           | Token reuse prevention                           | SEC-002        |
| 3.4-UNIT-002 | Unit        | P0       | Delete POST action has `[ValidateAntiForgeryToken]` attribute applied                                      | Attribute presence verification (static analysis) | SEC-002       |
| 3.4-E2E-009  | E2E         | P1       | Delete form in Details/List view contains `@Html.AntiForgeryToken()` call                                  | View includes anti-forgery token                 | SEC-002        |

## Recommended Execution Order

1. **P0 Unit tests** — Fail fast on attribute presence and configuration (3.4-UNIT-002, UNIT-005, UNIT-001)
2. **P0 Integration tests** — Security gates first (3.4-INT-002, INT-003, INT-004, INT-005, INT-010, INT-013, INT-014, INT-016, INT-019)
3. **P1 Integration tests** — Core functionality and logging (3.4-INT-001, INT-006, INT-007, INT-008, INT-011, INT-012, INT-015, INT-017, INT-020, INT-021, UNIT-003, UNIT-004)
4. **P1 E2E tests** — Critical user journeys and confirmation flows (3.4-E2E-001, E2E-002, E2E-004, E2E-005, E2E-006, E2E-007, E2E-008, E2E-009, E2E-010, E2E-011)

## Special Test Data Requirements

### Multi-User Test Data Setup
- **UserA** with 3-5 QR codes (various content types)
- **UserB** with 3-5 QR codes (for cross-user IDOR testing)
- At least one QR code with long label/content for display testing
- QR codes with `CreatedAt` timestamps spanning multiple days (for list verification)

### Test Scenario Execution Prerequisites
- Database seeded with test users and QR codes before integration tests
- Each test should use unique QR code IDs to avoid interference between tests
- Tests that delete records should either use isolated test data or restore database state after execution
