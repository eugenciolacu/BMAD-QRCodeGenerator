### AC7: Only the owner can download their QR code PDF — unauthorized access returns 404

| ID           | Level       | Priority | Test Description                                                                                                                           | Justification                                                        | Mitigates Risk |
|--------------|-------------|----------|--------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------|----------------|
| 4.1-INT-007  | Integration | P0       | GET `/QRCodes/DownloadPdf/{id}` as UserA with UserB's QR code ID (valid ID, wrong owner) → 404 returned; no PDF generated                  | Core IDOR prevention; critical AC                                    | SEC-001        |
| 4.1-INT-008  | Integration | P0       | GET `/QRCodes/DownloadPdf/{id}` as UserA with UserA's own QR code ID → 200 and valid PDF returned                                          | Owner can download their own QR code                                 | SEC-001        |
| 4.1-INT-009  | Integration | P0       | GET `/QRCodes/DownloadPdf/{nonExistentId}` → 404 returned; no exception or 500                                                              | Non-existent ID handled gracefully                                   | SEC-001        |
| 4.1-INT-010  | Integration | P0       | GET `/QRCodes/DownloadPdf/{id}?userId={UserB_Id}` — forged `userId` query parameter is ignored; only authenticated session's user ID used  | Parameter injection prevention; server always sources userId from session | SEC-001   |
| 4.1-INT-011  | Integration | P1       | After UserA's 404 response for UserB's QR code, query database → UserB's QR code record still exists unchanged                             | Verify unauthorized download did not mutate data                     | SEC-001        |

## Recommended Execution Order

1. **P0 Unit tests** — Fail fast on attribute presence (4.1-UNIT-005)
2. **P0 Integration tests — Security gates** — IDOR (INT-007, INT-008, INT-009, INT-010), auth (INT-015), QuestPDF licensing (INT-017), logging (INT-021)
3. **P0 Integration tests — Performance** — AC 8 compliance (INT-012)
4. **P1 Unit tests** — Service-level generation, metadata, logging (UNIT-001, UNIT-002, UNIT-003, UNIT-004, UNIT-006)
5. **P1 Integration tests** — Content correctness, headers, differential errors, remaining logging (INT-001, INT-003, INT-004, INT-006, INT-011, INT-013, INT-014, INT-016, INT-018, INT-019, INT-022, INT-023)
6. **P1 E2E tests** — UI entry points, filename, scannable QR, full happy path (E2E-001, E2E-002, E2E-003, E2E-005, E2E-006)
7. **P2 tests** — Edge cases, concurrency, layout review, null handling (INT-002, INT-005, INT-020, INT-024, E2E-004)

## Special Test Data Requirements

### Multi-User Test Data Setup
- **UserA** with 3–5 QR codes (varying `DecodedText` lengths and ECC levels)
- **UserB** with 3–5 QR codes (for cross-user IDOR testing; UserA must not own any of UserB's IDs)
- At least one QR code with a long `DecodedText` value (> 100 characters) to stress PDF layout
- QR codes with known, predictable `CreatedAt` timestamps for metadata assertion tests

### Test Scenario Execution Prerequisites
- QuestPDF Community license registered in test environment's `Program.cs` (or test startup fixture)
- Integration tests use an in-memory or isolated test database seeded before each test class
- Tests that assert on response times should run on a non-loaded CI machine; flag as flaky in resource-constrained environments
- E2E tests requiring manual PDF inspection (E2E-003, E2E-004) should be included in pre-release regression only, not automated CI
