## 1. Security

| Concern | Implementation | Status | Notes |
|---------|---------------|--------|-------|
| Authentication enforcement | `[Authorize]` inherited from `QRCodesController` class | ✅ Met | All actions require authentication; unauthenticated requests redirected to login |
| CSRF protection | `[ValidateAntiForgeryToken]` on Delete POST + `@Html.AntiForgeryToken()` in both delete forms | ✅ Met | Mitigates SEC-002; malicious cross-site delete requests blocked |
| IDOR prevention — ownership verification | `FirstOrDefaultAsync(q => q.Id == id && q.UserId == userId)` — atomic query with both predicates | ✅ Met | Mitigates SEC-001; user cannot delete another user's QR code by manipulating ID parameter |
| UserId from authenticated context | `userId` always from `User.FindFirstValue(ClaimTypes.NameIdentifier)` — never from request | ✅ Met | Prevents parameter tampering; userId cannot be forged via POST body or query string |
| 404 for unauthorized access | `if (qrCode == null) return NotFound();` for both non-existent and unauthorized IDs | ✅ Met | No data disclosure; attacker cannot enumerate valid IDs or determine ownership |
| No client-side only checks | Server-side ownership verification always performed; client confirmation is UX only | ✅ Met | JavaScript confirmation can be bypassed; server enforces all security |
| Rate limiting | Global fixed-window limiter (10 req / 10 s) in `Program.cs` | ✅ Met | Baseline DoS protection against deletion flood attacks |
| Parameterised queries | All DB access via EF Core (`FirstOrDefaultAsync`, `Remove`, `SaveChangesAsync`) | ✅ Met | No SQL injection risk |
| Secrets management | DB connection string in `appsettings.json` | ⚠️ Gap | Should use User Secrets (dev) or environment variable/Key Vault (prod). Same gap as other stories; not specific to delete. |

## 2. Performance

| Concern | Implementation | Status | Notes |
|---------|---------------|--------|-------|
| Database query efficiency | `FirstOrDefaultAsync` with indexed `Id` (PK) and `UserId` (FK with index) | ✅ Met | Index seek on both predicates; sub-millisecond query time |
| Single-record deletion | `Remove(qrCode)` followed by single `SaveChangesAsync()` | ✅ Met | Single DELETE statement; no over-fetching or N+1 issues |
| No unnecessary data loading | Only QR code entity loaded; no eager loading of related entities | ✅ Met | Minimal memory footprint |
| Redirect response time | `RedirectToAction(nameof(Index))` is immediate; no database query in redirect path | ✅ Met | Client receives 302 immediately after SaveChangesAsync |
| TempData overhead | Single string message in TempData; negligible cookie/session overhead | ✅ Met | No performance impact |
| Label truncation for logging | Label truncated to 50 chars before logging | ✅ Met | Prevents excessive log size for long DecodedText values |
| Overall response time | Expected < 50ms for typical deletion (query + delete + log + redirect) | ✅ Met | Acceptable for user-initiated action |

## 3. Reliability

| Concern | Implementation | Status | Notes |
|---------|---------------|--------|-------|
| Idempotent delete | `FirstOrDefaultAsync` returns null if already deleted; graceful 404 response | ✅ Met | Mitigates RACE-001; double-delete handled without error |
| Concurrent deletion | Two users cannot delete same QR code (ownership check); same user can submit twice but second returns 404 | ✅ Met | No race condition; EF Core transaction isolation handles concurrency |
| Database save failure | EF Core exceptions propagate to ASP.NET Core's unhandled exception middleware | ⚠️ Gap | No explicit try/catch around `SaveChangesAsync()`; DB failure returns 500 to user. Recommend wrapping in try/catch with user-friendly error message and Error-level log. |
| Invalid ID format | ASP.NET Core routing rejects non-integer IDs with 404 | ✅ Met | No exception thrown for `?id=abc` — handled by framework |
| Null ID handling | `int id` is non-nullable; framework requires a value | ✅ Met | No null ID can reach action method |
| Cascade delete integrity | EF Core cascade delete configured; no orphaned records if user is deleted | ✅ Met | Data integrity maintained at DB level |
| Log write failure | Serilog swallows log exceptions; deletion proceeds even if logging fails | ✅ Met | Logging failure does not block deletion |

| Concern | Implementation | Status | Notes |
|---------|---------------|--------|-------|
| Confirmation required | JavaScript `confirm()` dialog before POST submission on both Details and List pages | ✅ Met | Mitigates UX-001; prevents accidental deletion |

| Redirect to list | User redirected to My QR Codes list after deletion | ✅ Met | Natural flow; user sees updated list without deleted item |

| Button placement | Details: in card footer with Download buttons; List: disabled by default, enabled on row selection | ✅ Met | Consistent with other action buttons; not easily clicked by accident |

| Error feedback | 404 returns NotFound page (default ASP.NET Core 404 view) | ⚠️ Gap | Generic 404 page not user-friendly for "QR code not found" vs. "page not found". Recommend custom error view with message "QR code not found or access denied." |

## 7. Data Integrity & Privacy

| Concern | Implementation | Status | Notes |
|---------|---------------|--------|-------|
| Permanent deletion | `Remove(qrCode)` performs hard DELETE, not soft delete | ✅ Met | Matches architecture spec §3.5 "QR codes are immutable: only create, read, delete" |
| No orphaned records | `UserId` FK with CASCADE DELETE ensures QR codes deleted when user is deleted | ✅ Met | Bidirectional integrity; no manual cleanup needed |
| Transaction atomicity | EF Core wraps `SaveChangesAsync()` in implicit transaction | ✅ Met | Delete operation is atomic; no partial state |
| No data remnants | Entire QR code record removed; no "soft delete" flag or tombstone | ✅ Met | User data fully removed per request (GDPR right to erasure compliant) |
| Data isolation | `UserId` filter ensures users can only delete their own records | ✅ Met | No cross-user data access |
| No cascade side effects | QR codes have no dependent entities in current schema | ✅ Met | Delete is clean; no unexpected cascade deletions |
| Privacy on failure | 404 returned for both "not found" and "not owned" cases | ✅ Met | Prevents data disclosure; attacker cannot determine if ID exists |

## 9. Gaps & Recommendations Summary

| # | Severity | Concern | Recommendation |
|---|----------|---------|----------------|
| 1 | Low | Connection string in `appsettings.json` | Use ASP.NET Core User Secrets in dev; environment variable or Key Vault in production. (Not specific to delete; applies to entire app.) |
| 2 | Medium | No `try/catch` around `SaveChangesAsync()` | Wrap in try/catch; show user-friendly error (e.g., "Unable to delete QR code. Please try again.") and log at `Error` level on DB failure. Consistent with other stories. |
| 3 | Low | Generic 404 page for unauthorized deletion | Implement custom error view or error message in TempData: "QR code not found or access denied." Improves UX for legitimate users who encounter deleted or unauthorized QR codes. |
| 4 | Minor | Duplicate label truncation logic | Consider extracting truncation helper to utility class if used in multiple places (Index display, Delete logging, etc.). Low priority. |
