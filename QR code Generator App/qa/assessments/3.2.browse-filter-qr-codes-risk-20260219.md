# Risk Profile: Story 3.2 — Browse & Filter QR Codes

Date: 2026-02-19
Reviewer: Quinn (Test Architect)

---

## Executive Summary

- **Total Risks Identified:** 11
- **Critical Risks (score 9):** 1
- **High Risks (score 6):** 3
- **Medium Risks (score 4):** 4
- **Low Risks (score 2):** 3
- **Overall Story Risk Score:** 35/100 *(Base 100 − 20 critical − 30 high − 20 medium − 6 low)*

The Browse & Filter story's dominant risk is **data isolation**: failure to filter QR codes by the authenticated user's ID would expose every user's data to every other user — a direct IDOR vulnerability. Three high-severity risks follow: unauthenticated access, pagination count query missing the UserId filter (cardinality leak), and downstream action buttons not re-validating ownership. Medium risks cover search-term reflected XSS, unbounded page-size parameter abuse, conflated empty-state logic, and insufficient access logging. Low risks are minor UX edge cases.

---

## Critical Risks Requiring Immediate Attention

### 1. SEC-001: UserId Filter Omitted from List Query — Full Data Exposure (IDOR)

**Score: 9 (Critical)**
**Probability:** High (3) — EF Core does not automatically scope queries to the current user; a missing `.Where(q => q.UserId == currentUserId)` clause exposes the entire `QRCodes` table
**Impact:** High (3) — Every authenticated user could browse, filter, and view all other users' QR codes; severe privacy and IDOR violation

**Affected Components:** `QRCodesController (GET /QRCodes)`, LINQ query, `QRCodesContext`

**Mitigation:**
- The `Where(q => q.UserId == currentUserId)` clause must be the **first** filter applied before any search or pagination clause
- `currentUserId` must always be resolved from `HttpContext.User` (e.g., `User.FindFirstValue(ClaimTypes.NameIdentifier)`), never from a query string or route parameter
- Code review checklist: verify UserId filter is present in every overload/branch of the list action
- Integration test: create two users with separate QR codes; assert GET /QRCodes for User A returns only User A's records

**Testing Focus:**
- Test: Authenticated as User A → response contains only User A's QR codes; User B's records are absent
- Test: Manually forge `userId` query parameter → assert it is ignored; response still scoped to authenticated user
- Test: Unauthenticated request → 401/redirect to login (covered by `[Authorize]`)

## High Risks

### 2. SEC-002: Missing `[Authorize]` Attribute — Unauthenticated Access to List

**Score: 6 (High)**
**Probability:** Medium (2) — If `[Authorize]` is omitted from the controller class or action, the middleware pipeline will not challenge unauthenticated requests
**Impact:** High (3) — Unauthenticated visitors could reach the list action; combined with any data isolation gap this becomes a full data breach

**Affected Components:** `QRCodesController`, `Program.cs` (global auth policy)

**Mitigation:**
- Apply `[Authorize]` at the controller class level (not only on individual actions) so all QR code actions are protected by default
- Confirm global fallback policy or `RequireAuthenticatedUser()` is configured in `Program.cs`
- Automated test: unauthenticated GET /QRCodes → assert HTTP 302 redirect to `/Identity/Account/Login`

**Testing Focus:**
- Test: No auth cookie/token, GET /QRCodes → redirect to login page
- Test: Expired session cookie → redirect to login page; no data returned

---

### 3. SEC-003: Pagination Count Query Missing UserId Filter — Cardinality Leak

**Score: 6 (High)**
**Probability:** Medium (2) — A common pattern is to compute `totalCount = _context.QRCodes.Count()` separately from the paged query, forgetting to apply the UserId filter
**Impact:** High (3) — Pagination UI reveals the total number of QR codes across all users; leaks cardinality metadata and results in incorrect page calculations (showing "Page 1 of 500" to a user with 3 records)

**Affected Components:** `QRCodesController (GET /QRCodes)`, ViewModel (`QRCodesListViewModel.TotalPages`)

**Mitigation:**
- Both the data query and the count query must apply identical filters: `UserId == currentUserId` **and** the search predicate
- Prefer a single query with `CountAsync()` derived from the same `IQueryable` before pagination is applied: `var filteredQuery = _context.QRCodes.Where(q => q.UserId == currentUserId).Where(search predicate); var total = await filteredQuery.CountAsync(); var items = await filteredQuery.OrderByDescending(...).Skip(...).Take(...).ToListAsync();`

**Testing Focus:**
- Test: User A has 5 QR codes; User B has 100. User A's list shows total count = 5, pages calculated for 5 records only
- Test: User A applies search that matches 2 of 5 codes → total displayed is 2, not 5 or 100

---

### 4. SEC-004: Action Buttons (View Details / Download PDF / Delete) Do Not Re-Validate Ownership

**Score: 6 (High)**
**Probability:** Medium (2) — The browse list is the entry point for actions defined in Stories 3.3, 3.4, 4.1, 4.2; if those downstream controllers do not independently verify `QRCode.UserId == currentUserId`, a forged request ID in the URL/form can act on another user's record
**Impact:** High (3) — IDOR: attacker enumerates QR code IDs and issues Delete, Download, or View requests against records they do not own

**Affected Components:** `QRCodesController` (Details, Delete actions), `ExportController` (PDF download), linked Story 3.3, 3.4, 4.1 controllers

**Mitigation:**
- Every controller action that accepts a QR code ID **must** verify ownership before processing: `var qrCode = await _context.QRCodes.FirstOrDefaultAsync(q => q.Id == id && q.UserId == currentUserId); if (qrCode == null) return NotFound();`
- This check must be present in Stories 3.3, 3.4, 4.1, 4.2 as well; flag as cross-story dependency
- Never use `FindAsync(id)` alone for ownership-required operations

**Testing Focus:**
- Test: User A requests Details/Delete/Download for a QR code ID that belongs to User B → 404 returned; no data disclosed
- Test: User A's own QR code ID → action succeeds normally

## Medium Risks

### 5. SEC-005: Search Parameter Reflected in View Without Encoding — Reflected XSS

**Score: 4 (Medium)**
**Probability:** Medium (2) — If the search term is echoed into the view (e.g., `<input value="@Model.Search">` or inside a `<script>`) using `Html.Raw` or unescaped JS interpolation, the value could be exploited
**Impact:** Medium (2) — Razor auto-encodes `@Model.Search` by default in HTML context, but manual encoding mistakes in JavaScript blocks or `Html.Raw` calls would allow reflected XSS; session hijacking possible

**Affected Components:** `Views/QRCodes/Index.cshtml`, JavaScript row-selection code

**Mitigation:**
- Never use `Html.Raw` with user-supplied input (search term, page number, etc.)
- If injecting the search term into a JavaScript variable, use `@Json.Serialize(Model.Search)` rather than direct interpolation
- Verify Razor anti-XSS encoding is active for all `@Model.*` bindings in the view

**Testing Focus:**
- Test: Submit search = `"><script>alert(1)</script>` via GET query string → assert rendered HTML encodes the payload; no alert fires
- Test: Confirm `@Model.Search` appears in input's `value` attribute as encoded text, not raw HTML

---

### 6. PERF-001: Unbounded `pageSize` Parameter — User-Controlled Result Set Size

**Score: 4 (Medium)**
**Probability:** Medium (2) — If `pageSize` is accepted as a query parameter without a server-side cap, a malicious user can request `pageSize=100000` to fetch the entire user's QR code table in one call
**Impact:** Medium (2) — Memory pressure on the server; very slow response for users with large datasets; potential denial-of-service for other users on shared resources

**Affected Components:** `QRCodesController (GET /QRCodes)`, LINQ `Take()` clause

**Mitigation:**
- Hardcode `pageSize = 10` as a constant or read from app config; never accept it from the request
- If variable page sizes are desired in the future, enforce a maximum (e.g., `pageSize = Math.Clamp(requestedSize, 5, 50)`)

**Testing Focus:**
- Test: GET /QRCodes?pageSize=99999 → assert response contains at most `defaultPageSize` (10) records
- Test: pageSize not provided → defaults to 10

---

### 7. UX-001: Empty State Logic Conflates "No QR Codes" with "No Search Results"

**Score: 4 (Medium)**
**Probability:** Medium (2) — A single `if (Model.Items.Count == 0)` check with a generic "No QR codes found — Create one!" message is misleading when the user has QR codes but the search filters them out
**Impact:** Medium (2) — User believes they have no saved codes and navigates to Create, abandoning their search; poor UX and potential support confusion

**Affected Components:** `Views/QRCodes/Index.cshtml`, `QRCodesListViewModel`

**Mitigation:**
- Distingulish two empty states in the ViewModel: `IsEmptyLibrary` (user has zero QR codes at all) vs. `NoSearchResults` (user has QR codes but search filtered all out)
- `IsEmptyLibrary`: show "You haven't created any QR codes yet. [Create one]"
- `NoSearchResults`: show "No QR codes match your search. [Clear search]"

**Testing Focus:**
- Test: User with zero QR codes → empty-library message with Create link shown
- Test: User with 5 QR codes, search = "zzznomatch" → no-results message with Clear search option shown; no Create link

---

### 8. OPS-001: No Structured Logging for List Access Events

**Score: 4 (Medium)**
**Probability:** Medium (2) — List access events are typically not logged; there is no mention of logging in the story's Dev Notes
**Impact:** Medium (2) — Without access logs (UserId, search term, page, timestamp), forensic investigation of data exposure incidents is impossible; also required for compliance in some environments

**Affected Components:** `QRCodesController (GET /QRCodes)`, logging infrastructure

**Mitigation:**
- Log at `Debug` or `Information` level: `{UserId}`, `{Search}`, `{Page}`, `{ResultCount}`, `{IPAddress}`, `{Timestamp}`
- Do not log the full `DecodedText` of results (privacy); log only count and filter params
- Log at `Warning` level if `ResultCount == 0` and user has existing QR codes (potential search misconfiguration)

**Testing Focus:**
- Test: Issue GET /QRCodes with search and page params → assert log entry emitted with correct structured fields
- Test: Log does not contain individual QR code content (DecodedText)

## Low Risks

### 9. TECH-001: Page Number Out of Range — No Server-Side Boundary Enforcement

**Score: 2 (Low)**
**Probability:** Low (1) — Edge case; users rarely manually manipulate `?page=` in URLs
**Impact:** Medium (2) — A page number beyond the last page returns an empty list with no indication to the user that the navigation is out of bounds; confusing UX

**Mitigation:**
- Clamp `page` parameter: `page = Math.Max(1, Math.Min(page, totalPages))`; redirect to last valid page if out of range
- Or: return page 1 silently if out-of-range value is provided

**Testing Focus:**
- Test: GET /QRCodes?page=9999 when only 1 page exists → clamped to page 1; no error; no empty list shown

---

### 10. TECH-002: Row-Selection JavaScript State Lost on Page Navigation

**Score: 2 (Low)**
**Probability:** Medium (2) — Standard JS in-memory row selection is cleared on page reload or pagination click
**Impact:** Low (1) — Minor UX annoyance; no data loss or security implication; user must re-select a row after navigating pages

**Mitigation:**
- Acceptable for MVP; document as known UX limitation
- Future enhancement: persist selection in `sessionStorage` or highlight the last-navigated-from record

---

### 11. BUS-001: No Feedback When Buttons Are Clicked Without Row Selected

**Score: 2 (Low)**
**Probability:** Low (1) — AC 7 specifies buttons are disabled until a row is selected; if JS is disabled or the disabled state is not enforced consistently, buttons may appear clickable
**Impact:** Medium (2) — Clicking an action button with no row selected would submit a null/empty ID to a controller action, potentially surfacing an unhandled exception

**Mitigation:**
- Buttons must have `disabled` attribute set in Razor (`asp-disabled`) and the `disabled` state toggled only via JS after row selection
- Server-side action must validate that `id` parameter is non-null/non-zero; return 400 if not

**Testing Focus:**
- Test: POST/GET to View Details, Delete, or Download with no `id` → returns 400 or graceful error, not 500

## Risk-Based Testing Strategy

### Priority 1: Critical Risk Tests
1. **SEC-001** — Two users, each with separate QR codes; GET /QRCodes as User A → assert only User A's records returned
2. **SEC-001** — Forge `?userId=<UserB_Id>` query param → assert it is ignored; response still scoped to authenticated user
3. **SEC-001** — Unauthenticated GET /QRCodes → 302 redirect to login; no QR code data in response

### Priority 2: High Risk Tests
4. **SEC-002** — Remove auth cookie; GET /QRCodes → HTTP 302 to `/Identity/Account/Login`
5. **SEC-003** — User A has 3 QR codes; User B has 100; User A's page footer shows "Page 1 of 1" and total = 3
6. **SEC-003** — User A searches with matching term; count = matched subset only, not all QR codes in DB
7. **SEC-004** — User A requests GET /QRCodes/Details/{UserB_QRCodeId} → 404; no data disclosed
8. **SEC-004** — User A posts DELETE for User B's QR code ID → 404; record not deleted

### Priority 3: Medium / Low Risk Tests

10. **PERF-001** — GET /QRCodes?pageSize=99999 → response contains ≤10 records
11. **UX-001** — User with 5 QR codes, search "zzznomatch" → "no results" message (not "create first code" message)
12. **UX-001** — New user with zero QR codes → "no QR codes yet, create one" message with Create link
13. **OPS-001** — Structured log entry with `{UserId}`, `{Search}`, `{Page}`, `{ResultCount}` emitted on each GET
14. **TECH-001** — GET /QRCodes?page=9999 (only 1 page) → clamped response; no 500 error
15. **BUS-001** — GET /QRCodes/Details with no `id` → 400 or redirect; no unhandled exception

## Risk Acceptance Criteria

### Must Fix Before Production
- **SEC-001** — UserId filter applied before any other query clause; sourced from `HttpContext.User` only (Critical)
- **SEC-002** — `[Authorize]` confirmed on controller class; unauthenticated access blocked (High)
- **SEC-003** — Count query uses same `IQueryable` with UserId filter as data query (High)
- **SEC-004** — All downstream action controllers verify `QRCode.UserId == currentUserId` before returning data or executing mutations (High)

### Can Deploy with Mitigation
- **SEC-005** — Razor default encoding covers HTML context; verify no `Html.Raw` usage with user input (Medium)
- **PERF-001** — Hardcode `pageSize = 10`; remove any user-configurable page size until intentionally designed (Medium)
- **UX-001** — Two distinct empty-state branches in view; low effort, reduces support confusion (Medium)
- **OPS-001** — Add one structured log call; low effort (Medium)

### Accepted Risks
- **TECH-001** — Clamp page number; acceptable UX enhancement for MVP
- **TECH-002** — Row-selection state loss is expected browser behavior; document as known limitation
- **BUS-001** — Disable attribute enforced via JS; server-side null check for defense in depth; accepted at MVP scale

## Monitoring Requirements

Post-deployment monitoring:
- **SEC-001**: Alert on any query to `QRCodes` table that is missing a `WHERE UserId =` predicate (DB-level query monitoring or EF Core query interception)
- **OPS-001**: Structured log query for `QRCodeListAccessed` events; alert on error spikes or anomalous search patterns
- **PERF-001**: P95 response time for GET /QRCodes; alert if >300ms (list queries should be fast with index on `UserId, CreatedAt`)
- **SEC-002**: Alert on 401/302 responses from QR code routes to detect auth bypass attempts
