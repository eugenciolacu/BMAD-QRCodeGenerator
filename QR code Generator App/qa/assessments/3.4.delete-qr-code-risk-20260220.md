## Executive Summary

- **Total Risks Identified:** 10
- **Critical Risks (score 9):** 2
- **High Risks (score 6):** 3
- **Medium Risks (score 4):** 3
- **Low Risks (score 2):** 2
- **Overall Story Risk Score:** 44/100 *(Base 100 − 36 critical − 30 high − 15 medium − 5 low)*

The Delete QR Code story presents significant security and usability risks. The two critical concerns are **unauthorized deletion via IDOR** (allowing users to delete others' QR codes) and **CSRF attacks due to missing or bypassable anti-forgery protection**. High-severity risks include missing authorization checks, accidental deletion without proper confirmation, and insufficient audit logging. The permanent nature of deletion amplifies the impact of any failure in these controls.

---

## Critical Risks Requiring Immediate Attention

### 1. SEC-001: UserId Ownership Not Verified Before Deletion — IDOR Vulnerability

**Score: 9 (Critical)**
**Probability:** High (3) — Without explicit ownership verification, any authenticated user could delete another user's QR code by manipulating the ID parameter
**Impact:** High (3) — Unauthorized deletion of user data; potential data loss attack; violation of data integrity and user trust

**Affected Components:** `QRCodesController (POST /QRCodes/Delete/{id})`, authorization logic

**Mitigation:**
- The delete action **must** verify ownership before deletion: `var qrCode = await _context.QRCodes.FirstOrDefaultAsync(q => q.Id == id && q.UserId == currentUserId);`
- Return `NotFound()` (404) if the record doesn't exist or belongs to another user — never reveal whether the ID exists
- **Never** use `FindAsync(id)` followed by a separate ownership check; the query must include both predicates atomically
- The `currentUserId` must always be resolved from `HttpContext.User.FindFirstValue(ClaimTypes.NameIdentifier)`, never from client input
- Code review checklist: verify ownership filter is present and cannot be bypassed

**Testing Focus:**
- Test: User A attempts to delete User B's QR code (valid ID, wrong owner) → 404 returned; no deletion occurs
- Test: User A deletes own QR code → success; record removed from database
- Test: Delete with non-existent ID → 404 returned
- Test: Forged UserId in request body/query string is ignored; only authenticated user's ID is used

---

### 2. SEC-002: Missing or Bypassable Anti-Forgery Token — CSRF Attack Vector

**Score: 9 (Critical)**
**Probability:** High (3) — If the `[ValidateAntiForgeryToken]` attribute is omitted or the token is not properly included in the DELETE form, attackers can trigger deletion via CSRF
**Impact:** High (3) — Attacker can trick authenticated users into deleting their QR codes via malicious links or embedded forms on external sites

**Affected Components:** `QRCodesController (POST /QRCodes/Delete/{id})`, Razor views (Details, List pages), form markup

**Mitigation:**
- Apply `[ValidateAntiForgeryToken]` attribute to the DELETE POST action
- Include `@Html.AntiForgeryToken()` in every delete form on Details and List pages
- Ensure the form uses `method="post"` — never use GET for deletion operations
- If using JavaScript confirmation, ensure the POST request includes the anti-forgery token in headers or form data
- Global anti-forgery middleware in `Program.cs` should be enabled

**Testing Focus:**
- Test: POST to /QRCodes/Delete/{id} without anti-forgery token → 400 Bad Request or validation error
- Test: POST with valid token from same session → deletion succeeds
- Test: Attempt to reuse a token from a previous page load → rejected
- Test: Cross-site POST with no token → blocked by anti-forgery validation

## High Risks

### 3. SEC-003: Missing `[Authorize]` Attribute — Unauthenticated Deletion

**Score: 6 (High)**
**Probability:** Medium (2) — If `[Authorize]` is omitted from the controller class or the delete action, unauthenticated users could reach the endpoint
**Impact:** High (3) — Combined with other vulnerabilities, this could allow anonymous deletion attempts; even if ownership checks prevent actual deletion, it exposes the endpoint unnecessarily

**Affected Components:** `QRCodesController`, action attributes

**Mitigation:**
- Apply `[Authorize]` at the controller class level to protect all actions by default
- Verify global authentication policy is configured in `Program.cs` (`RequireAuthenticatedUser()`)
- Integration test: unauthenticated POST to delete endpoint → 302 redirect to login or 401 Unauthorized

**Testing Focus:**
- Test: No auth cookie/token, POST to /QRCodes/Delete/{id} → redirect to login; no deletion occurs
- Test: Expired session → redirect or 401; no deletion occurs

---

### 4. UX-001: Missing or Inadequate Confirmation Mechanism — Accidental Deletion

**Score: 6 (High)**
**Probability:** Medium (2) — If confirmation is not implemented or easily bypassed, users may accidentally delete QR codes with a single click
**Impact:** High (3) — Permanent data loss; users cannot recover deleted QR codes; poor user experience and potential support burden

**Affected Components:** UI (Details/List pages), JavaScript confirmation, optional confirmation page

**Mitigation:**
- Implement a confirmation mechanism: either JavaScript `confirm()` dialog or a dedicated confirmation page (GET /QRCodes/Delete/{id})
- The confirmation message should clearly identify which QR code will be deleted (show label/content)
- Consider implementing a two-step delete: mark as deleted with a grace period before permanent removal (out of scope for MVP, but note for future)
- User acceptance testing should validate the confirmation flow

**Testing Focus:**
- Test: Click delete without confirming → no deletion occurs
- Test: Confirm deletion → QR code is deleted and user redirected with success message
- Test: Cancel confirmation → user returns to previous page unchanged
- Manual UX test: ensure confirmation clearly identifies the target record

---

### 5. AUD-001: Deletion Event Not Logged or Insufficient Audit Trail

**Score: 6 (High)**
**Probability:** Medium (2) — If deletion logging is omitted or incomplete, security incidents and data integrity issues cannot be investigated
**Impact:** High (3) — No audit trail for deletions; cannot detect unauthorized deletions or troubleshoot user complaints; compliance risk

**Affected Components:** `QRCodesController (POST /QRCodes/Delete/{id})`, logging configuration, `ILogger<QRCodesController>`

**Mitigation:**
- Log every deletion attempt: `_logger.LogInformation("User {UserId} deleted QR code {QRCodeId} with label '{Label}' at {Timestamp}", currentUserId, id, qrCode.Label, DateTime.UtcNow);`
- Log failed deletion attempts: `_logger.LogWarning("User {UserId} attempted to delete QR code {QRCodeId} - not found or not owned", currentUserId, id);`
- Include: user ID, QR code ID, label/content preview, timestamp, IP address (optional)
- Ensure logs are persisted to durable storage (file, database, or external service)
- Define log retention policy per compliance requirements

**Testing Focus:**
- Test: Delete own QR code → verify log entry contains user ID, QR code ID, label, timestamp
- Test: Attempt to delete another user's QR code → verify warning log with user ID and attempted QR code ID
- Review: Log entries do not contain sensitive data (e.g., full QR code content, tokens)

## Medium Risks

### 6. DATA-001: Orphaned Related Data or Cascade Delete Misconfiguration

**Score: 4 (Medium)**
**Probability:** Low (1) — EF Core cascade delete is configured correctly per architecture (§3.5), but implementation errors could leave orphaned records
**Impact:** High (3) — Database integrity issues; orphaned records accumulate; potential foreign key violations in future queries

**Affected Components:** `QRCodesContext`, `OnModelCreating`, EF Core migration

**Mitigation:**
- Verify cascade delete configuration in `QRCodesContext.OnModelCreating`: `modelBuilder.Entity<QRCode>().HasOne<User>().WithMany().HasForeignKey(q => q.UserId).OnDelete(DeleteBehavior.Cascade);`
- Integration test: delete a QR code → verify no orphaned records in dependent tables (if any are added in future)
- Database constraint test: manually verify foreign key relationships and cascade rules
- Architecture note confirms "QR codes are immutable: only create, read, delete" — no complex dependencies expected

**Testing Focus:**
- Test: Delete QR code → verify record is removed from database (no soft delete marker left behind)
- Test: Check foreign key constraints are properly configured in migration scripts
- Future-proofing: if related tables are added later (e.g., QR code analytics), ensure cascade behavior is defined

---

### 7. RACE-001: Concurrent Deletion Attempts or Double-Delete

**Score: 4 (Medium)**
**Probability:** Low (1) — Low probability in single-user scenarios, but possible in API contexts or rapid double-clicks
**Impact:** High (3) — First request succeeds; second request encounters a missing record; if not handled gracefully, may return 500 error or confusing message

**Affected Components:** `QRCodesController (POST /QRCodes/Delete/{id})`, LINQ query

**Mitigation:**
- Idempotent delete: if the record doesn't exist (already deleted), return success or a benign 404 — do not throw an exception
- Use `FirstOrDefaultAsync` followed by a null check: `if (qrCode == null) return NotFound();` — this handles both "never existed" and "already deleted" cases identically
- Ensure any confirmation page fetches the latest record state before showing the form
- Transaction isolation: rely on EF Core's default transaction behavior; no explicit locking needed for single-record deletes

**Testing Focus:**
- Test: Submit two concurrent delete requests for the same QR code → first succeeds, second returns 404 (no exception thrown)
- Test: Delete a QR code, then access its delete confirmation page again → 404 or appropriate error message

---

### 8. UX-002: Redirect Target or Success Message Missing or Confusing

**Score: 4 (Medium)**
**Probability:** Medium (2) — If redirect logic is incomplete or TempData is not set, users may see a blank page or unclear outcome
**Impact:** Medium (2) — Poor user experience; user uncertainty about whether deletion succeeded; may attempt deletion again

**Affected Components:** `QRCodesController (POST /QRCodes/Delete/{id})`, redirect logic, TempData, List view

**Mitigation:**
- After successful deletion, redirect to `/QRCodes` (My QR Codes list) with TempData success message: `TempData["SuccessMessage"] = "QR code deleted successfully."; return RedirectToAction("Index");`
- List view must display TempData message prominently (Bootstrap alert or similar)
- If deletion fails (404), show an error message or redirect with error TempData
- Ensure the redirect target page loads correctly and displays the updated list (deleted QR code is absent)

**Testing Focus:**
- Test: Delete QR code → redirected to /QRCodes; success message displayed; deleted QR code does not appear in list
- Test: Delete attempt fails (invalid ID) → error message displayed; user remains on appropriate page
- Manual UX test: confirm message is visible, clear, and dismissible

## Low Risks

### 9. PERF-001: Database Query Performance for Deletion

**Score: 2 (Low)**
**Probability:** Low (1) — Single-record deletion by primary key is inherently fast; no complex joins or aggregations
**Impact:** Medium (2) — Even under high load, impact is minimal; only becomes a concern if deletion is combined with complex cascades (not present in MVP)

**Affected Components:** `QRCodesContext`, database indexes

**Mitigation:**
- Ensure `Id` is indexed (it's the primary key, so this is automatic)
- Monitor deletion query performance in production logs
- If future features add dependent tables, review cascade delete performance

**Testing Focus:**
- Load test: perform 100 deletions in succession → verify average response time is acceptable (< 200ms)
- Review: SQL query plan for DELETE statement is efficient (index seek, not table scan)

---

### 10. UX-003: Delete Button Placement or Styling May Encourage Accidental Clicks

**Score: 2 (Low)**
**Probability:** Low (1) — With proper confirmation, accidental clicks are mitigated; still a minor UX concern
**Impact:** Medium (2) — Even with confirmation, frequent accidental clicks create friction and frustration

**Affected Components:** UI (Details/List pages), CSS, button styling

**Mitigation:**
- Use destructive action styling (e.g., red button, warning icon) to signal danger
- Place delete button in a secondary position (not the primary action)
- Consider separating delete button from other action buttons (e.g., right-align or place in dropdown menu)
- Front-end design spec should address this (cf. front-end-spec.md)

**Testing Focus:**
- Manual UX review: delete button is clearly labeled, visually distinct, and appropriately positioned
- Usability test: confirm users understand the delete action and are not confused by button placement

## Testing Recommendations

### Priority 1 (Critical Path)
- Ownership verification: User A cannot delete User B's QR code
- Anti-forgery protection: POST without token is rejected
- Authorization: Unauthenticated users cannot access delete endpoint

- Deletion events are logged with sufficient detail for audit trail

- QR code is permanently removed from database after deletion
- No orphaned records or cascade issues

- Delete button is clearly styled and positioned
- Error messages are clear and actionable
- Performance is acceptable under normal and high load
